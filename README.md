# Loan Portfolio Control Board

A portfolio-monitoring dashboard for a small-ticket, daily-repayment credit lender, built with Streamlit.
It answers the questions a credit-operations lead asks every morning: *How risky is the book? What changed since
yesterday? Which loans need attention right now?*

> **Data notice:** all data in this repository is **simulated**. It was generated by
> [`synthetic/generate.py`](synthetic/generate.py) to mimic patterns typical of an average credit lender:
> daily instalments, a minority of borrowers who fall behind or default, varying collections performance
> across officers, and so on. The parameters are illustrative and are **not calibrated to, or derived from,
> any real institution**. No real borrower, lender or transaction data is used. Amounts are in Kenya shillings (KES).

## What is on the page

1. **Verdict row:** PAR% as the headline (with state badge and change vs the previous snapshot), plus tiles for collection efficiency, book size and interest realization, each with a sparkline.
2. **Trend and "what changed":** PAR across snapshots, and new loans / closures / newly-in-Loss / newly-cold since the last snapshot.
3. **Needs attention:** exceptions (no payment for 30+ days, early defaults, newly in Loss) on the page rather than buried in a tab.
4. **Tabs for depth:** *Risk* (PAR bands, loss severity, collateral, plan deviation, concentration), *Collections* (efficiency, follow-up lists, champion leaderboard), *Portfolio* (branch and product exposure, yield, vintage), *Data & system* (pipeline health, assumptions).

Every number, flag and threshold is defined in [`GLOSSARY.md`](GLOSSARY.md).

## How it fits together

```
synthetic/generate.py   simulates borrowers, repayments, arrears, write-offs
        |               and writes 30 daily raw exports (80-column layout)
        v
etl.py                  cleans, engineers the risk/collections metrics, loads
        |               loans_snapshot (history) + loans_current (latest) + pipeline_run_log
        v
data/loan_portfolio.db  bundled SQLite database (what the deployed app reads)
        v
dashboard/data.py       cached read; filtering happens in pandas
dashboard/metrics.py    metric formulas
dashboard/charts.py     Altair charts
app.py                  layout
```

The ETL and the schema are the production-style pipeline; the synthetic generator emits the raw layout that
pipeline expects, so nothing downstream is special-cased for the demo. [`schema_sqlite.sql`](schema_sqlite.sql) is the
SQLite dialect of [`schema.sql`](schema.sql): same tables, same columns.

## Run it

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

# the bundled database is committed, so this is all you need:
LOAN_DB_URL=sqlite:///data/loan_portfolio.db streamlit run app.py
```

Rebuild the database from scratch (about a minute; regenerates the exports and runs them through the ETL):

```bash
python -m synthetic.build_demo
```

Tune the simulated lender in [`synthetic/params.py`](synthetic/params.py) (default rates, product mix, champion
quality spread, write-off timing, seed) and rebuild.


## Pointing at a different database

`config.SQLALCHEMY_URL` uses `LOAN_DB_URL` if set, otherwise falls back to the MySQL settings in `config.py`.
The app reads through SQLAlchemy and contains no dialect-specific SQL, so MySQL or Postgres only needs the
corresponding DDL ([`schema.sql`](schema.sql) is the MySQL original).
